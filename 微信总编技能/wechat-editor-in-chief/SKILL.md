# 微信总编 · WeChat Editor-in-Chief

把一个主题、一组素材、一个观点或一份初稿，发展成适合目标读者、内容扎实、读起来顺畅、可以进入公众号编辑器的文章。默认先搜集资料和素材，再综合分析、选择角度、组织创作；不要收到题目就凭印象直接扩写。负责统筹与验收，不替代下游写作和配图技能。

不绑定账号、作者、行业、文体或视觉风格。研究为文章服务：评论需要证据与推理，故事需要可信细节与叙事，指南需要可执行步骤，随笔需要感受与观察。不要把每篇文章都写成产品评测、论证报告或新闻综述。

## 技能协作

写作或润色前，从当前技能目录定位并读取 **human-writing（人味写作）** 的 SKILL.md；配图阶段定位并读取 **words-to-visuals（文字成画）** 的 SKILL.md，按其引用读取必要参考文件。常见位置分别为 `~/.agents/skills/human-writing/SKILL.md` 和 `~/.codex/skills/words-to-visuals/SKILL.md`；以本次环境的技能目录为准，不绑定某台电脑。缺失时说明具体依赖，继续独立工作，不声称已调用。

人味写作负责自然叙述、修改与去除空话；文字成画负责视觉方向、图像计划、素材生产和图像验收。精确图表使用确定性绘图工具；生成插画按文字成画的 imagegen 路由执行。技术产品的资料查询遵守适用的官方文档技能。

沿用用户已给出的授权和选择，不重复确认。配图遵循文字成画的方向、样图两道确认；用户明确要求一次完成时按该技能的一次交付例外执行。仅选方向不等于已经批准样图。不要把制作文章理解成授权上传、登录或发布。

## 编辑流程

### 1. 建立简报

先读当前对话、用户素材、已有稿件和项目参考目录（如 `REF`）。识别用户提供的是主题、素材、观点还是初稿，提取文章目的、读者、账号定位、署名、口吻、时效、篇幅和交付要求。已知信息直接沿用，只问会实质改变成稿且无法推断的缺口；其他情况说明合理假设并推进。未指定账号和署名时不要自行填入旧项目资料。字数和图片数按内容需要决定。

主题是研究入口，素材是待理解与核对的材料，观点是待检验和发展的判断，初稿则是已有表达。不要要求用户先交完整大纲；也不要把用户观点直接当成已经证实的事实。用户明确只润色、不补资料或仅使用指定素材时遵守范围。

### 2. 搜集资料与综合分析

先读 [研究与选材](references/research-and-angle.md)，按输入建立研究问题，主动搜集必要的背景、事实、案例、故事细节、数据、相关观点与视觉素材线索。涉及可查事实时同时使用 [资料与事实核验](references/evidence.md)。按题材选择原始资料与可靠来源，不把检索结果摘要直接当成证据。

搜集后先综合分析：哪些材料相互印证，哪里存在冲突或空缺，什么最值得读者知道，用户的原有观点是否需要修正。确定文章的中心问题、叙事线或核心判断，再选择有用素材与结构；不要先定死结论再只找支持材料。向用户简要交代有价值的发现和拟采用角度，除非确有方向分歧，不额外设大纲审批关卡。

### 3. 写作与通俗化

应用 human-writing 写作模式；已有稿件则使用润色模式。按题材选择叙述、解释、评论、访谈整理、指南等表达方式，用段落推进内容，避免资料堆砌、空洞赞美和模板化转折。专业程度跟随目标读者，通俗不等于浅薄。指南可使用必要步骤，比较可使用表格，不为统一风格损害实用性；用户明确的文体要求优先。

开头尽快建立阅读理由，正文围绕主线展开，结尾停在有分量的判断、余味或具体行动上。标题与内容相符，可按需要给少量不同角度的备选；避免夸大、假悬念和正文无法兑现的承诺。

不要用“我让 AI 写了这篇文章”交代幕后过程，除非用户要创作手记；也不要为增加人味编造作者亲测、经历、感受或对话。必要的素材来源与 AI 图像标识照常保留。自然表达不等于保证通过 AI 检测。涉及记忆或偏好档案修改时遵守用户授权，不自动持久化。

用户提出修改时沿原稿继续，保留已接受的要求。改完再逆向核对事实，包括标题、结论和图注，避免“口语化”改变原意。

### 4. 配图与图表

文章主线稳定后，按需要应用 words-to-visuals，完成诊断、方向选择、样图和整组制作。图片可以承担氛围、叙事、说明、证据或操作指引的作用；按文章选择摄影、插画、资料图、流程图或数据图，不强制每篇配图表。区分概念插画与真实记录；人物、事件、截图与数据不能用生成图伪造证据。涉及图表时保留数据、单位、口径与来源，可读性不足时拆图。用户要求纯文字时不强加图片。

逐张查看成品，确认文字、数据、裁切、手机可读性；记录放置位置、用途、alt、图注、来源、权利状态和生成提示词。按信息价值决定数量，不固定封面加若干张。

### 5. 排版与复制正文

交付前必读 [HTML 发布规范](references/html-publishing.md)。用 `scripts/render_wechat.py` 与 `assets/wechat.html` 从同一份文章 JSON 生成 Markdown 和 HTML；复杂版式可扩展，但保留复制边界与降级机制。

HTML 的核心是点击“复制正文（带格式）”后，把 **仅正文** 的 `text/html` 与 `text/plain` 放到剪贴板。标题独立复制，操作按钮和使用说明不得混入。正文样式写在元素上，图片离线内嵌并另交原文件。不能保证本地图片粘贴进微信后仍保留，因此提供图片下载和明确检查提示。

检查桌面和手机宽度、所有图片加载、正文复制范围、标题复制及失败提示。可以用页面内剪贴板替身验证载荷，不能冒称测试过系统剪贴板或微信后台。每次改稿同步更新 MD、HTML、图注、摘要和评论区结论。

### 6. 交付

完整创作默认提供 Markdown、HTML、实际使用的独立图片和素材 ZIP；按文体提供摘要及一句适合分享或评论区的表达，不把故事、散文硬压成论点。资料密集文章附来源与复核记录，配图附素材清单。用户仅需草稿或局部修改时按范围交付。交代真实完成的检查与尚存限制；本地文件交付无需额外发布确认，实际发布需要用户授权。

## 最终验收

- 文章回应用户的主题、素材或观点，适合目标读者；文体与内容目的相符。
- 已完成必要的资料搜集与综合分析，文章有清晰主线，材料经过取舍而非拼贴。
- 事实、时间、人物、数字、引用和图片一致；观点、推断与虚构的边界明确。
- 没有编造个人体验，也没有无关的幕后写作过程。
- 每张图有用途且已检查；概念图与真实资料可区分。
- MD 与 HTML 同稿；复制载荷没有标题、按钮或脚本；失败不假报成功。
- 图片可单独取得，文件可打开，交付说明不夸大微信兼容性。
