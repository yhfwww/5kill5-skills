# 追问技能说明文档

## 1. 技能概述

`second-question`（追问）是一个帮助用户发现认知盲点的 AI Agent Skill。它根据当前对话、用户提供的素材，以及已知的项目背景或历史偏好，提出一个可能改变后续决策的问题。

它的核心主张是：**不给答案，只给用户没想到的下一个问题。**

这个技能关注未经检验的前提、尚未比较的选择，以及反复出现却没有被察觉的模式。每次最多问一个问题；如果找不到足够有价值的问题，就放弃追问，回到正常对话。

## 2. 适用场景与边界

适合在以下场景中使用：

- 已经形成一个方案，希望检查自己是否漏掉了关键前提。
- 做出了技术、产品或业务决策，但还没有认真考虑备选方案。
- 对某个判断非常确信，希望有人挑战其中未经验证的假设。
- 讨论多轮仍在同一路径上打转，需要重新审视目标本身。
- 一个具体话题已经讨论充分，希望找到能推动下一步行动的问题。

以下情况不应自动插入追问：

- 用户正在要求具体命令、检查代码细节，或执行明确的步骤。
- 用户要求直接给结果，或明确表示结束整段对话、整个任务。
- 没有足够的内容信号，或者刚刚已经追问过。
- 只能提出通用、重复、诱导性或不影响决策的问题。

### 与需求澄清助手的区别

| 对比项 | 追问 `second-question` | 需求澄清 `req-clarifier` |
| --- | --- | --- |
| 主要目标 | 发现用户尚未意识到的认知盲点 | 补全需求信息，形成可执行规格 |
| 典型问题 | 如果你依赖的前提不成立，当前选择还成立吗？ | 预算多少、目标用户是谁、何时上线？ |
| 输出方式 | 每次最多一个贴合背景的问题 | 结构化整理与少量关键澄清问题 |
| 成功标准 | 回答后可能改变判断或下一步选择 | 信息更完整，需求更明确 |

预算、用户、期限等信息收集问题，即使对执行任务很重要，也不属于本技能的核心职责。

## 3. 目录结构

```text
追问/
├── 技能说明.md
└── second-question/
    └── SKILL.md
```

- `second-question/SKILL.md`：技能入口，定义触发规则、问题类型、生成流程和输出规范。
- `技能说明.md`：面向使用者的说明，介绍用途、调用方式和预期行为。

当前技能以文本规则为主，目录中没有配套脚本、模板或外部服务配置。

## 4. 如何使用

在支持并已加载该技能的 Agent 环境中，可以通过技能名称或自然语言发起请求。最好同时提供正在考虑的选择、作出判断的理由，以及让你不踏实的地方；也可以直接沿用当前对话背景。

**直接调用：**

```text
second-question 帮我戳一下这个想法：我们准备按生成次数收费，因为生成得越多，用户得到的价值就越大。
```

**自然语言触发：**

```text
这个方案我总觉得哪里有问题但说不上来，帮我想想我漏了什么。
```

**围绕已有讨论追问：**

```text
基于刚才讨论的上线计划，问我一个可能改变这个决定的问题。
```

不必先填写完整问卷。没有可用的历史记忆时，应使用当前对话和用户提供的素材定制问题，不能编造用户经历或偏好。

## 5. 触发机制

### 用户主动请求

“问我个问题”“追问我”“戳一下我这个想法”等直接请求，以及“帮我想想我漏了什么”“这个思路有没有漏洞”等隐式请求，都会启动追问流程。

用户主动要求时，语气可以更直接，但仍需满足问题质量标准。启动技能不等于必须问出一个问题。

### 对话中自动触发

自动触发按以下顺序判断，任一步不通过就停止：

1. **先检查否决信号**：用户是否正在执行明确任务，或希望结束整段对话？如果是，不插入追问。
2. **再检查内容信号**：是否出现未经检验的断言、未说明权衡的决策、隐约的重复模式、讨论停滞，或尚未落到行动的子话题？至少命中一项才继续。
3. **最后检查节奏**：距离上次反问，应至少经历一次话题切换，或间隔至少 6–8 轮对话；自动触发次数还应低于建议的每段对话 2–3 次软上限。达到软上限后，仅在用户主动要求时追问。

一个子话题里的“先这么定”，只有在讨论充分但尚无具体行动、且通过其他检查时，才可能触发行动收敛问题。用户明确要结束整个任务时，应停止追问。

## 6. 五类问题与生成流程

| 问题类型 | 关注点 | 典型信号 |
| --- | --- | --- |
| 苏格拉底追问 | 判断依据是否经过检验 | “肯定是”“用户当然会”等断言 |
| 反事实假设 | 核心前提不成立时，选择是否仍合理 | 已作决定，但没有说明备选方案的权衡 |
| 类比迁移 | 熟悉领域的经验能否揭示当前问题 | 隐约重复的做法，或在陌生领域遇阻 |
| 根本假设质疑 | 目标本身是否值得继续追求 | 同一路径讨论超过 3–4 轮仍无实质进展 |
| 行动收敛 | 什么具体行动能推动下一步 | 子话题已讨论深入，但没有可执行动作 |

每次只选择最贴合情境的一类，结合具体背景构造一个问题，再检查反模式和质量标准。问题不合格时先重构；反复重构仍不合格，就弃权。

输出以问题本身为主。如需分析铺垫，控制在两三句以内。主动请求时可以直接提问；自动插入时语气应更柔和，第一次插入要明确允许用户跳过。

## 7. 示例交互

以下示例展示输出方向，实际提问应根据当次对话定制。

### 主动请求：检查定价前提

**用户：**

> 我们准备按 AI 报告的生成次数收费，生成越多价值越大。帮我戳一下这个想法。

**追问：**

> 如果同一位用户生成十次，是因为前九份报告都不满意，你按次数收费的模型会把什么当作“价值”？

这个问题把“使用次数”与“获得价值”之间未经验证的关系暴露出来，答案可能影响收费单位的选择。

### 自动插入：检查用户接受度

**用户：**

> 我们这个面向普通写作者的工具，用户当然愿意自己填 API key，能省钱就行。

**追问（通过触发与节奏检查后）：**

> 顺手问一句：你对这批普通写作者“愿意自带 API key”的判断，依据的是他们实际完成配置的经历，还是他们对省钱的口头认可？（不想展开可以跳过）

### 不触发：明确执行任务

**用户：**

> 定价先不讨论了，把价格页上的“每月 29 元”改成“每月 39 元”。

**预期行为：**完成明确的修改任务，不自动插入定价追问。

## 8. 质量标准

每个问题都必须同时通过“哇塞测试”的两层检验：

- **认知意外**：能否让用户意识到自己刚才没有考虑过的点？
- **决策分量**：答案是否可能改变下一步选择或方案质量？

问题还必须贴合具体背景。如果原封不动地换给一个完全不了解的用户仍然适用，就需要重新构造。

以下问题应被过滤：

- 可以直接查资料得到答案的问题。
- 用户已经回答过，或只是换一种说法重复的问题。
- 预算、期限等单纯收集信息的问题。
- “你还满意吗”等礼貌性问题。
- “要不要考虑用某个框架”等伪装成问题的建议。
- “你不觉得风险很大吗”等暗含答案、诱导认同的问题。

**宁可漏问，不可滥问。** 没有提出问题，也可能是技能正确判断后的结果。

## 9. 维护建议

- 调整触发规则或输出规范时，以 `second-question/SKILL.md` 为准，并同步更新本文档。
- 保留“否决信号 → 内容信号 → 节奏信号”的自动触发顺序，避免变成模糊的综合判断。
- 新增示例时，检查是否夹带建议、预设立场或退化成信息收集。
- 保留每次最多一个问题、允许跳过和不合格时弃权的约束。
- 验证时同时覆盖主动请求、自动触发、明确执行任务、用户结束对话和触发过密等情况。
