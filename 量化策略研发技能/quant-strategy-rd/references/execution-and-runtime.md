# 执行与运行时安全

策略的目标仓位不是已成交仓位。以下原则用于单腿和多腿系统、中心化交易所和链上交易的共同执行边界。

## 1. 订单生命周期与权威状态

将每次动作建模为显式状态，例如：

```text
PLANNED → SUBMISSION_STARTED → ACKNOWLEDGED → FILLED
                                  ├→ REJECTED/CANCELLED
                                  └→ PARTIAL_OR_UNKNOWN → NEEDS_REPAIR
```

- `SUBMISSION_STARTED` 必须在进入外部下单边界前持久化，包含动作/批次 ID、幂等键、预期订单和当时风险快照。进程崩溃后不能据此推断“肯定未下单”。
- “创建订单成功”“收到 API ACK”“交易签名已广播”均不等于成交。以订单终态、累计成交、平均价格、费用与精确的实际持仓增量共同确认。
- 多腿批次或合并逻辑节点的会计按唯一订单/交易签名去重；将每个节点都当成独立现金流会重复计费。
- 部分成交、未知响应、重复回报、签名冲突、仓位增量不匹配或超时，均应停止新的风险增加。保留原始证据并标记需要修复；不要静默把状态改为成功、FLAT 或重新发送新订单冒充重试。

## 2. 并发、恢复与退出

- 每个账户/策略范围内只允许一个协调决策者写账本和提交订单。后台成本查询、监测、网页控制台和恢复逻辑不得另建交易决策链。
- 使用跨进程/跨实例锁及持久化的动作 ID；本地锁无法阻止另一台机器、另一个容器或同一账户的其他策略交易。
- 开仓和加仓可以需要新鲜行情及时间确认；退出、减仓、人工暂停和已触发的风险动作应有更高优先级。退出触发后锁定意图，先处理未完成开仓的成交/取消竞态，再根据实际仓位完成退出。
- 从重启恢复时，以交易所/链上真实事实、未完成订单、成交记录和本地事件账本逐笔对账。停止程序不等于平仓；删除 state、锁或 pending 不能解决不一致。

如果无法安全归因，系统可以保持只读监测和 HALTED/NEEDS_REPAIR 状态，但不得自动用假设补齐仓位。

## 3. 风控独立性

下单前的独立风险检查至少覆盖：账户余额与可用保证金、总名义、单标的/单腿名义、净敞口、杠杆与保证金模式、清算距离、最大亏损/回撤、最大持仓时间及连续异常。使用预期订单叠加实际持仓后的投影暴露；任何限额触发则整批拒绝或按明确的降险规则处理。

多腿策略还要检查：每条腿是否都可下、取整后是否仍保持允许的对冲偏差、单腿失败时的处理方式，以及不由该策略管理的同账户仓位。应优先防止裸露风险，而非强行完成目标篮子。

风险关键配置需 schema 和跨字段校验，控制台默认只监听本机或受认证的私有网络。不能让任意页面提交未知字段、覆盖路径、修改运行状态或绕过硬风控。

## 4. 配置、密钥与审计

- 将策略/经济配置与运行时状态分离。为经济参数生成配置指纹并写入每个周期/持仓；不兼容变更在有仓位时须阻断、迁移或先安全归零，不能用删除字段绕过检查。
- 密钥、钱包、真实运行状态、原始可广播交易、私有账本与备份不进入源码、发布包、示例配置或普通研究材料。日志只保留恢复与审计所需的最小字段。
- 记录配置 diff、版本、操作者/来源、时间、是否带仓和是否重启。运行事件要能关联数据快照、信号、风险结果、订单 ID/签名、持仓核对、退出原因和错误元数据。
- 健康监测默认诊断与告警；不要因健康检查失败就自动重启、强杀、清锁或继续交易。磁盘、时钟、数据新鲜度和日志写入失败都属于交易安全信号。

## 5. 最小运维检查表

启动前确认：配置可验证、环境正确、行情完整而新鲜、时间同步、状态与实际仓位一致、未完成订单可解释、风险限额正确、日志和磁盘可用、控制面受保护。先运行 dry-run，再考虑受限实盘。

发生异常时：停止新的交易决策；查询真实仓位、未完成订单和近期成交；用动作/批次 ID 关联本地证据；由操作者决定补单、减仓、平仓或接受现状；备份后修正状态；重新验证并先以 dry-run 复演。只在证据闭环后恢复实盘。
