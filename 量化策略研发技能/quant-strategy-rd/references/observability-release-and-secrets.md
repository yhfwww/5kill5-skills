# 可观测性、发布与密钥

本参考面向要持续运行或部署到服务器的策略。选择实现强度时应与资金、账户共享程度、服务数量和恢复难度相称；不要求单机小策略搭建大型遥测平台。

## 1. 可关联的运行证据

对策略事件、订单事件、风险决策和错误使用稳定的关联字段，例如 `strategy_id`、`run_id`、`event_id`、`config_fingerprint`、`data_snapshot_id`、`order_batch_id`、外部订单/交易 ID 和发生时间。所有可执行策略的权威事件流采用 [代理可分析日志](agent-readable-logging.md) 中的 JSONL 契约；数据库、平台日志或遥测系统可作为索引、检索或聚合层。目标是能从一个异常订单追到其数据、信号、风险判断和发布版本。

将日志、指标和健康状态分工：日志解释事件，指标揭示趋势和阈值，健康状态回答是否可安全继续。最小指标通常包括进程/心跳、数据年龄、订单状态、对账差异、风险拒绝、异常率、磁盘/日志写入和账户连接。告警表需明确触发条件、严重度、通知目标、人工操作和何时禁新单；告警渠道不应依赖唯一可能已故障的策略进程。

## 2. 可验证发布

每次服务器发布至少生成或记录一个非敏感 `release-manifest.json`（或等价文件）：代码 commit/tag、构建时间、运行时版本、依赖锁文件哈希、发布物哈希、配置 schema、数据库/状态迁移版本、测试/回放证据和已知限制。生产运行状态记录正在执行的版本和配置指纹。

风险较高或多人协作项目可额外生成依赖清单（SBOM）和构建来源证明；其目标是回答“这个服务器正在运行什么、由哪些输入构建、是否与批准版本一致”，而不是为了满足某个工具形式。发布与回退都需检查运行中状态的兼容性，不能拿旧状态覆盖已变化的外部账户事实。

## 3. 密钥生命周期与最小权限

维护一份不含实际值的密钥清单：用途、环境、可用权限、拥有者、存储位置、失效/轮换机制、吊销步骤、依赖方和泄露联系人。优先使用可撤销、最小权限、可审计、按环境隔离的凭据；交易权限、提现权限、部署权限与只读监控权限不应无必要共享。

密钥不得进入代码、示例、运行脚本、命令行参数、错误日志、发布物、截图或研究笔记。为轮换和疑似泄露准备可演练的流程：先阻断凭据或交易权限，评估未完成订单与服务器访问，再更新服务配置、验证最小功能并记录处置。密钥轮换不应被误解为策略可自动恢复实盘。

## 4. 事故与恢复演练

为高影响系统记录最短事故手册：谁可禁新单、怎样取得只读账户事实、怎样保存证据、如何通知、何时可以恢复。定期在不影响真实资金的环境中演练至少一种数据故障、执行故障和发布/恢复故障；更新手册和策略研究笔记中的发现。恢复判定以新鲜外部事实、完整对账、健康检查和授权为基础，不以“进程已重启”作为依据。
