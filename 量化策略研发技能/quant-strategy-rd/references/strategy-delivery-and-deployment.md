# 策略交付与跨平台部署

本参考适用于需要长期运行、可托管到服务器的策略。它定义的是交付最低面，不授权自动部署、启动实盘、修改服务器或使用账户凭据；这些操作仍需用户明确授权。

## 1. 每个可部署策略的仓库交付物

每个策略仓库应包含以下可直接使用的产物：

| 类型 | Windows | Linux | 要求 |
|---|---|---|---|
| 操作入口 | 根目录的 `启动实盘.cmd`、`停止程序.cmd`、`重启实盘.cmd`、`查看运行状态.cmd`、`查看实时日志.cmd` | `scripts/start-live.sh`、`stop-live.sh`、`restart-live.sh`、`status.sh`、`tail-logs.sh` | 两端命令语义、输出字段、退出码和配置选择保持一致 |
| 环境 bootstrap | 根目录的 `安装配置环境.cmd` | `scripts/bootstrap-env.sh` | 在一台新机器上安装锁定依赖、创建非敏感配置骨架并执行诊断；不启动实盘 |
| 统一 launcher | PowerShell 或项目 CLI | Bash 或项目 CLI | 业务程序只保留一套启动/检查逻辑；桌面/服务器脚本均委托给它 |
| 网页控制台（仅在需要时） | 现有 launcher 入口或单独的 `启动网页服务.cmd`/`查看网页服务状态.cmd` | 现有 launcher 入口或同语义脚本 | UI 与核心进程分离时才增加独立入口；状态必须包含绑定地址、HTTPS/反向代理期望与健康结果 |
| 版本发布 | `build-release` 与 `verify-release` 的 Windows 入口 | 语义相同的 Bash/项目 CLI 入口 | 生成并校验独立的 `<策略名>-<版本号>` 发布目录/压缩包 |
| 服务器文件 | Windows Task Scheduler 的任务导入/创建说明（若需要开机恢复） | `deploy/<strategy>.service` systemd unit | 服务只使用受限账户、绝对路径和明确的环境文件 |
| 文档 | `docs/策略研究笔记.md`、`docs/日志与事件规范.md`、`docs/服务器部署运行指南.md`、运行手册 | 同左 | 文档与实际脚本、日志 schema、配置字段、版本和端口一致 |

脚本名可保留中文以方便 Windows 交付；Linux 的文件名采用 ASCII。不要依赖双击窗口、交互式 shell profile、当前工作目录、映射盘或开发机的绝对路径。

只有确实交付网页界面时，增加 `docs/网页控制台使用与安全说明.md`，写明它是只读监控、研究工具还是可提交受控操作意图；绑定地址、远程访问边界、认证角色、反向代理/TLS、状态/健康接口与其不会执行的动作。详细架构与验证见 [网页控制台与操作界面](web-console-and-operator-ui.md)。

版本化打包的目录布局、清单字段、排除项和验收方式见 [版本化发布包](versioned-release-packaging.md)。

## 2. 脚本的行为契约

所有入口先定位自身所在的项目根目录，并调用一个项目内的 launcher/CLI。launcher 应至少支持 `bootstrap`、`doctor`、`start`、`stop`、`restart`、`status`、`logs`；它是唯一了解 PID、日志路径、锁、健康检查、运行时命令与状态文件位置的地方。

对于代理或自动化诊断，launcher 还应提供等价的只读机器接口（例如 `status --json` 与事件 JSONL 路径），而不是要求解析本地化的人类控制台文字。详细字段、敏感信息边界和测试要求见 [代理可分析日志](agent-readable-logging.md)。

| 命令 | 应做什么 | 不应做什么 |
|---|---|---|
| start | 校验环境、配置 schema、运行时依赖、单实例锁、状态/未完成订单和数据/健康前置条件；明确启动哪种模式 | 自动生成宽松的实盘配置、绕过状态不一致、用旧状态覆盖当前事实 |
| stop | 请求业务程序优雅停止，等待有限时间，报告 PID/退出结果和“是否仍有仓位未知” | 视为平仓、删除状态/锁、默认强杀或清理 pending |
| restart | 先完成 stop 的检查，再重新执行 start 前置条件 | 盲目 kill 后立即启动、跳过对账或配置变化检查 |
| status | 只读输出进程、锁、配置版本、健康/最近心跳、数据新鲜度、状态摘要、日志位置和告警 | 输出密钥、私密交易字节、完整真实账本，或修改交易状态 |
| logs | 显示带时间戳的最近日志并可持续跟随，明确关闭窗口不会停止服务 | 反向触发服务停止、把日志路径硬编码为开发机路径 |
| bootstrap | 在运行前检查平台/架构、锁定运行时与依赖来源；按项目锁文件安装依赖，创建受限目录和仅在缺失时复制的非敏感配置模板，再运行 `doctor`/配置校验 | 猜测语言或包管理器、接受未锁定版本、覆盖真实配置、把密钥写入参数/日志、启动实盘/服务/计划任务 |
| doctor | 只读输出运行时版本、依赖完整性、配置是否存在且 schema 有效（不回显敏感值）、目录权限、时钟/磁盘/网络前置条件及可执行下一步；支持 `doctor --json` | 修改交易配置、访问账户、自动修复未知状态或以“已安装”代替验证 |

Windows 的 `.cmd` 应使用 `%~dp0` 定位根目录，设置 UTF-8 控制台，并委托 PowerShell `-NoProfile` 或项目 CLI；在 Windows 上调用 Node 包管理器时兼容 `npm.cmd`。Linux Bash 脚本应从脚本路径解析根目录，使用 `set -eu`（按项目需要决定 `pipefail`），检查可执行权限与运行时版本。两端要返回非零退出码给调用者，且不要将密钥通过命令行参数或 echo 输出。

### 一键安装与配置环境

`安装配置环境.cmd` 和 `scripts/bootstrap-env.sh` 是同一个 `bootstrap` 语义的交互式/非交互式入口，不是将开发机环境复制到服务器。实际项目应通过锁文件、`bootstrap` 配置或同版本发布记录声明所支持的 OS/架构、精确运行时版本、依赖命令、可信来源与（适用时）安装文件哈希；脚本只执行已声明的路径。若目标缺少许可软件、企业代理、GPU 驱动或人工发放的运行时，必须清晰失败并指出人工前置条件，不能下载不明脚本或静默降级到其他版本。

`bootstrap` 至少按下列顺序执行并把阶段、版本、非敏感路径、结果、退出码和 `run_id` 写入独立 JSONL bootstrap 日志：

1. 获取单实例锁，定位项目根目录，检查 OS、架构、磁盘空间、权限和受支持的运行时；失败时不留下半配置状态。
2. 验证发布包/依赖锁文件及已批准来源；只安装确切版本。网络安装应使用项目明示的官方/内部源及哈希验证；不可验证时停止。
3. 使用项目实际的可复现命令安装依赖（如 `npm ci`、带哈希的 Python 依赖或已锁定的二进制清单），并输出实际版本清单。
4. 创建日志、状态和配置目录及其最小权限；仅在真实配置不存在时从 `config.example.*` 复制骨架。绝不覆盖现有配置、状态、数据库或订单证据，也不收集或回显密钥。
5. 运行离线的配置 schema 校验和 `doctor --json`；可以检查本地依赖、目录、时钟和网络前置条件，但不得连接账户、提交订单、启动服务、注册 Task Scheduler/systemd 或启动实盘。
6. 成功时输出下一步的显式命令（例如编辑配置、执行 dry-run、经授权后启动）；失败时保留诊断证据并以非零退出码结束。

为避免交互脚本阻塞自动化，Linux 和 CI 入口应支持文档化的 `--non-interactive` 模式：所有缺失的必填非敏感选择必须失败而不是猜测。密码、私钥、API secret 和助记词不得作为命令行参数；若项目需要凭据，bootstrap 只说明受控存储位置、最小权限和后续人工配置步骤。Windows 的双击 wrapper 沿用下方的停留窗口契约；服务、CI 与 Task Scheduler 调用无 `pause` 的 launcher `bootstrap` 命令。

### Windows 双击入口

六个中文 `.cmd` 文件（包括 `安装配置环境.cmd`）是给操作者双击使用的交互式 wrapper，必须符合以下要求：

- 无论 launcher 成功、校验拒绝或异常退出，窗口都显示输出并等待操作者按键；不得在失败路径跳过等待，也不得用重定向吞掉标准错误。
- wrapper 保存 launcher 的退出码，显示成功/失败摘要，在 `pause` 后以同一退出码退出。它必须先 `cd /d "%~dp0"`，因此从桌面、快捷方式或任意工作目录双击都有相同行为。
- `查看实时日志.cmd` 默认持续跟随日志；操作者以 `Ctrl+C` 结束跟随之后，窗口仍停留以查看最后输出。`查看运行状态.cmd` 也在显示状态后等待。
- 服务进程、Windows Task Scheduler、远程部署和自动化测试不得调用带 `pause` 的 wrapper；它们调用相同 launcher 的非交互命令，以免后台任务永久阻塞。

项目应根据实际 launcher 填入命令；下列结构是 wrapper 的最低形态，而不是把策略命令写死到技能中：

```bat
@echo off
setlocal EnableExtensions
chcp 65001 >nul
cd /d "%~dp0"
title <strategy> - <action>

call scripts\launcher.cmd <action>
set "exitCode=%ERRORLEVEL%"

echo.
if not "%exitCode%"=="0" echo 操作失败，退出码：%exitCode%
echo 按任意键关闭此窗口。
pause >nul
exit /b %exitCode%
```

如果 launcher 是 `node`、`python` 或 PowerShell 文件，直接调用该运行时并同样在其后保存 `%ERRORLEVEL%`；只有调用另一个 `.cmd`/`.bat` 时才使用 `call`。发布前应在目标 Windows 环境中通过资源管理器双击每个入口，分别验证成功、配置错误、运行中状态、日志跟随与 `Ctrl+C` 返回后的窗口行为。

优雅停止信号和等待时间取决于运行时：Linux 服务应处理 `SIGTERM`；Windows 应通过应用程序的受支持控制接口或受控子进程停止。只有用户明确选定、且优雅停止在超时后仍失败时，才提供单独的强制停止路径。无论何种停止方式，必须说明它不会关闭已有仓位。

## 3. 长期策略研究笔记

创建 `docs/策略研究笔记.md`，并在研究、策略变更、实盘审计或故障复盘中有重要新证据时维护它。它不是运行日志，也不保存密钥、完整账本或可广播交易。

采用如下结构，并让内容随策略发展而更新：

```markdown
# <策略名>研究笔记

## 当前结论摘要
| 结论 | 结论属性 | 证据范围 | 策略/配置版本 | 最近复核 |

## 当前策略基线
- 信号、时间粒度、目标仓位、风险边界、退出和成本口径。

## 研究与实验记录
### YYYY-MM-DD — <问题>
- 假设：
- 数据与方法：
- 结果和反例：
- 结论属性（已验证/观察/推断/待验证）：
- 可复现证据位置：

## 实盘/模拟观察与故障复盘
## 参数与模型决策记录
## 未解决问题与下一步验证
## 变更记录
```

明确区分“代码实现了”“离线回放通过”“dry-run 观察到”“只读账户核对”和“实盘成交/长期净盈利”。策略参数、版本、数据范围或成本口径变更后，旧结论不能无说明地沿用。

## 4. 服务器发布与首次运行指南

在每个策略的 `docs/服务器部署运行指南.md` 中根据实际项目填写以下步骤。不要给出虚构的 IP、账户、密钥、钱包地址或生产命令；所有 `<占位>` 必须替换为该策略确认过的真实、非敏感项目字段。

### 发布前（在开发或 CI 环境）

1. 固定待发布的 Git commit/tag，记录版本、依赖锁文件和文件哈希；只发布明确的文件清单。
2. 运行离线测试、配置验证和 dry-run/回放验证，记录结果及未覆盖项。
3. 生成不含 `.env`、密钥、钱包、运行时状态、私有账本、日志、数据库和开发缓存的发布包，或由服务器以只读方式检出已批准 tag。
4. 提供 `config.example.*` 与环境变量清单，说明每项是否属于经济参数、是否会影响带仓状态、以及修改后是否需要迁移或重启。

### Windows Server

1. 创建专用、非管理员的服务账户和仅该账户可写的应用目录；不要以 Administrator 或交互式个人账户运行策略。
2. 从发布包或只读 Git tag 部署代码后，以服务账户双击/运行 `安装配置环境.cmd`；它安装与锁文件兼容的运行时和依赖、创建非敏感配置骨架，并记录 `--version` 输出与包哈希。未通过 bootstrap 不得进入后续步骤。
3. 用 ACL 创建仅服务账户可读的环境文件；从示例配置创建真实配置。密钥不进 Git、任务计划命令行、`.cmd`、日志或共享盘。
4. 在该账户上下文中执行配置验证与不下单的 dry-run。确认日志目录、数据目录、时钟同步、磁盘空间、网络出口和数据健康检查。
5. 用 `启动实盘.cmd`/`查看运行状态.cmd` 验证 launcher；若要开机恢复，使用 Windows Task Scheduler 在服务账户下调用 launcher 的受限启动命令。任务只在所有安全前置条件通过时恢复，不能因异常自动清状态或重下单。
6. 对外管理界面默认绑定 `127.0.0.1`。远程访问须通过 VPN 或有认证、TLS、IP 白名单和审计的反向代理；不要将交易控制端口裸露公网。

### Linux Server（systemd）

1. 创建无登录权限的专用用户、应用目录和日志/状态目录；代码目录只读或由受控发布账户写入。
2. 从固定 tag 或校验过的发布包部署，以服务用户运行 `scripts/bootstrap-env.sh` 安装锁定依赖并执行 `doctor --json`；使用 `umask 077` 创建仅服务用户可读的环境文件。
3. 编写并检查 `deploy/<strategy>.service`：`User=`、`WorkingDirectory=`、`EnvironmentFile=`、`ExecStart=` 与绝对路径，`Restart=` 仅覆盖明确可安全重启的进程退出。不要把密钥写在 unit 文件或 `ExecStart` 参数中。
4. 先在服务用户身份下执行配置验证、离线/DRY 模式及健康检查，再 `systemctl daemon-reload`、`enable`、`start`。通过 `systemctl status`、`journalctl -u <strategy>` 和策略自身的只读 status 确认。
5. 配置最小网络权限、防火墙、时间同步、日志轮转、磁盘告警和备份。备份只含必要的状态与审计证据，采用加密和最小权限，不复制密钥或可广播交易。

### 升级、回退与异常处置

1. 记录现网版本、配置指纹、状态摘要、未完成订单和真实仓位；发生不一致时先对账而非升级。
2. 用 `停止程序`/`stop-live.sh` 优雅停止并确认进程退出。不要把“已停止”当作“已平仓”。
3. 备份必要的状态和审计证据到受保护位置，部署新 tag，安装锁定依赖并再次验证配置兼容性。
4. 先 dry-run/只读检查，再按授权启动；启动后核对健康、数据新鲜度、状态、真实持仓与最近事件。
5. 回退仅回退已验证的代码和匹配的配置；绝不以旧状态文件覆盖继续变化中的账户事实。

## 5. 跨平台代码标准

- 在应用逻辑中使用相对项目路径或语言的路径库，不拼接 `C:\\...`、`/home/...`，也不依赖 shell 的当前目录。
- 将进程、时间、文件锁、信号与环境变量访问放入可替换的运行时适配层；Linux 与 Windows 都需要单实例、原子写入和优雅退出的测试。
- 锁定依赖并分别验证 Windows Server 与 Linux 的安装命令。避免仅 Windows 可用的批处理、注册表、COM 或仅 Linux 的 `/proc` 逻辑进入核心策略。
- 使用 UTF-8、明确时区（内部优先 UTC）和跨平台换行；文档中分别给出 PowerShell 与 Bash 命令。
- 在两种目标系统各做一次冷启动、重复 start、stop、restart、日志跟随、状态读取、进程异常后恢复和 dry-run 验收。声明哪些验证实际已完成，哪些仍待目标服务器验证。
