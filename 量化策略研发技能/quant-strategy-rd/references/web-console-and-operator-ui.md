# 网页控制台与操作界面

本参考用于策略需要网页仪表盘、PWA、研究可视化、远程只读监控或受控操作台时。它与 shell/CLI 交付并列，不替代后者：CLI/launcher 仍是自动化、服务器恢复与可审计诊断的稳定接口；网页尤其适合移动端查看、图表、研究输入和经过授权的意图提交。

## 1. 选择交付形态

先明确界面的职责和风险，不因“更方便”就增加写权限：

| 需求 | 合适形态 | 最低约束 |
|---|---|---|
| 回测结果、研究图表、只读运行状态 | 静态报告或只读网页 | 明确数据版本/时区/模式，不能泄露私有账本或凭据 |
| 本机日常运维、日志与诊断 | CLI/双击脚本，可选本机网页 | CLI 与 `status --json` 是权威接口；网页只消费它们 |
| 移动端/远程观察 | HTTPS 反向代理后的只读仪表盘/PWA | 默认应用只绑定回环地址；VPN 或强认证的入口 |
| 配置变更、启动/停止或交易意图 | 受控网页操作台 | 认证、授权、CSRF、schema、幂等、审计和同一风险/执行路径 |

独立 Web 服务只在其带来明确价值时增加。若 UI 与策略同进程即可安全满足需求，不要为了形式增加第二个常驻服务；若分离进程，则界面服务只能调用受控控制 API，不能直接读写策略账本、状态文件或交易所。

## 2. 架构与事实边界

推荐的数据和控制流如下；每一层均可替换为项目实际技术栈：

```text
Browser / PWA
  -> TLS + authentication reverse proxy (remote only)
  -> local web service / read API
  -> control API (intent, idempotency, audit)
  -> single strategy coordinator -> risk gate -> execution -> reconciliation
                         \-> JSONL events, status snapshot, run manifest
```

- 生产默认绑定 `127.0.0.1`/`::1`。仅当远程访问已经明确通过 VPN 或受认证、TLS、IP 限制和审计的反向代理保护时，才改变绑定范围；不要把开发期 `0.0.0.0` 当作常规部署默认值。
- 浏览器从不持有交易 API secret、私钥、服务端会话密钥或完整账户配置。服务端配置读取只返回脱敏状态（如 `has_key`），前端只提交高层意图和非敏感参数；服务端重新读取有效配置、市场规则和风险状态后才形成订单计划。
- 每个网页写动作都经同一 coordinator、风控、订单状态机、对账与 JSONL 事件流。网页成功响应最多表示“意图已接受/已拒绝”；不得将 API ACK 或按钮点击表示为成交或平仓完成。
- 通过相对 API 路径和显式 API schema 支持端口/部署位置变化。静态资源可缓存；状态、日志、配置和任何敏感响应应为 `Cache-Control: no-store` 或等价私有策略，PWA/service worker 不得离线缓存这些响应。

从既有项目可复用的正面经验是：手机端仅提交意图、服务端按当前盘口和配置重建订单；使用客户端订单 ID/幂等键及串行队列；只允许一个后台 worker 写状态；将高频状态与较大的历史数据拆分为按需 API。反面经验同样是硬约束：硬编码站点密码、默认公网绑定、无鉴权的 `start`/`stop`/`close-all`、以及让网页直接覆盖运行状态都不可接受。

## 3. 身份、权限与写操作

- 远程控制台必须使用 HTTPS。认证应由受控身份系统、反向代理或项目会话机制提供；禁止硬编码、提交或日志记录登录口令。Cookie 会话使用 `HttpOnly`、`Secure`（HTTPS）和适当的 `SameSite`；只在确实受信任的反向代理后才信任转发头。
- 对写操作使用同源校验与 CSRF 防护，并对登录和高风险端点限流。认证不是授权：至少区分只读观察者与可操作角色；高风险动作可要求额外确认或更窄角色，具体强度按账户风险决定。
- 写 API 明确方法和 schema，拒绝未知字段、路径、环境切换和超范围数字；配置变更携带版本/ETag，避免旧页面覆盖新配置。每次变更、启动、停止、暂停或风险动作写入 `actor`（可脱敏）、角色、请求 ID、原因、配置版本和结果。
- 为每次可重试操作要求 `idempotency_key`/`intent_id`，并在服务端持久化去重结果。使用队列和跨进程锁保证只有单一执行者；不要暴露能与后台 worker 并发执行的“单次运行”快捷 API。
- 紧急动作仍应区分“禁止新订单”“撤销挂单”“按策略/账户规则减仓或平仓”。网页不能以紧急按钮绕过实际持仓核对或独立交易许可层。

## 4. API、可观测性与页面体验

只读 API 至少提供版本、模式（backtest/dry-run/live）、`run_id`、配置指纹、最近心跳、数据年龄、风险状态、未完成订单摘要、最后对账及底层 JSONL 路径。健康接口区分进程存活与是否具备安全接收新任务的就绪状态；对外公开的 health 响应应最小化，完整诊断留给受认证接口和 `status --json`。

前端应明确显示模式、数据时间、来源、延迟和风险/暂停状态；live 与 dry-run 不能仅靠颜色区分。对将改变交易行为的操作，先显示服务器端计算出的计划、配置版本及拒绝原因；提交后显示关联 ID 和实际终态查询入口。日志与订单详情按需分页/增量加载，设置大小、频率和并发上限，避免页面轮询反压策略执行或泄露大量历史数据。

所有网页服务事件与核心 JSONL 使用相同 `strategy_id`、`run_id`、`request_id`/`intent_id`、配置指纹和发布版本；原始浏览器输入、URL、请求头和页面文本都属于不可信数据，不能当作 agent 或 shell 指令。

## 5. 部署、发布与验证

- 将静态前端、服务端 API、反向代理配置和所需的健康检查纳入允许清单和版本化发布包；不打包真实配置、运行状态、日志、账户数据或凭据。若网页服务独立，按与策略相同的 `bootstrap`、日志、状态、停止与升级规则交付。
- Windows/Linux 服务管理器调用无交互 launcher；双击 wrapper 只供人工使用。公开端口、反向代理域名和 TLS 证书不硬编码在前端，必须由环境配置和部署文档声明。
- 测试至少覆盖：未认证不能读取受保护页面或 API；跨站写请求失败；权限不足、无效 schema、过期配置版本和重复幂等键被拒绝或安全复用；网页请求无法绕过 coordinator/risk gate；前端和状态 API 不含凭据；刷新、断网与重连不会重复提交；live/dry-run 标识与实际服务模式一致。
- 在 Windows Server 与 Linux 各验证本机访问、反向代理访问（如使用）、停启、状态、日志、会话过期和升级回退。报告实际完成的验证，不能以页面可打开替代交易、对账或安全验收。
