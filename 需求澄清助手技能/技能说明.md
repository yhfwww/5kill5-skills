# 需求澄清助手技能说明文档

## 1. 技能概述

`req-clarifier` 是一个面向需求分析和产品定义的 AI Agent Skill，用于把用户模糊、零散、口语化的需求描述整理为结构化需求文档，并通过少量高价值追问补齐关键缺口。

该技能不是一次性生成 PRD 的简单模板，而是一套迭代式需求澄清流程。它强调先整理已知信息，再识别缺口、提出优先级最高的问题，并在多轮对话中逐步提高需求完整度，最终输出可执行的需求规格文档。

## 2. 适用场景

适合在以下需求中使用：

- 用户只有一个产品、功能、项目或业务流程的初步想法，需要先梳理清楚。
- 用户提供了一段口语化需求，需要整理成结构化需求规格。
- 用户想写 PRD、功能说明、开发需求、MVP 范围或项目启动材料。
- 用户描述的软件、AI 产品、数据分析、工作流自动化、设计项目等需求存在信息缺口。
- 用户需要识别目标、用户、功能范围、约束、风险和开放问题。
- 用户要求在开工前发现需求矛盾、边界不清、资源限制或关键假设。

不适合直接用于：

- 需求已经完全明确，只需要进入编码、设计或交付物制作的任务。
- 只需要改写一句话、翻译、润色标题等轻量文本任务。
- 用户明确要求不要追问、不要澄清，而是直接执行某个确定动作。

## 3. 目录结构

```text
需求澄清助手技能/
├── 技能说明.md
└── req-clarifier/
    └── SKILL.md
```

各文件用途：

- `req-clarifier/SKILL.md`：技能入口文件，描述触发条件、需求澄清流程、整理模板、评分规则和最终需求规格文档模板。
- `技能说明.md`：当前文档，用于说明技能用途、使用方式、输出标准和维护要点。

## 4. 使用前准备

使用该技能前，可以让用户自由描述需求，不要求格式完整。已有信息越多，澄清效率越高。

| 信息项 | 说明 | 示例 |
| --- | --- | --- |
| 需求背景 | 为什么要做这件事，当前有什么问题 | 现有审批流程靠微信群沟通，容易遗漏 |
| 目标用户 | 谁会使用或受影响 | 销售、财务、主管、外部客户 |
| 核心目标 | 做成后希望解决什么 | 缩短审批周期，减少人工核对 |
| 功能范围 | 必须做、希望做、暂时不做的内容 | 表单提交、审批流、通知、统计报表 |
| 成功标准 | 如何判断需求完成或有效 | 审批时长下降 50%，错误率低于 1% |
| 约束条件 | 时间、预算、技术栈、团队、人力 | 2 周内上线，现有系统是企业微信 |
| 风险假设 | 未验证前提和可能失败点 | 用户是否愿意切换到新流程 |

如果用户只给出一句话，也可以直接启动技能，先输出初步整理和关键追问。

## 5. 标准工作流程

### 第一步：接收并结构化整理

先把用户已经提供的信息完整归类，不遗漏细节。对尚未确认的信息使用 `[待确认]` 标注，避免把推断写成事实。

整理时优先覆盖：

- 背景与问题
- 目标与成功标准
- 目标用户和利益相关方
- 功能范围
- 资源与约束
- 假设与风险

### 第二步：识别缺口并追问

根据已知信息识别最影响决策的缺口，每轮只问 2 到 4 个问题。问题按优先级排列：

1. 先问战略层问题，例如目标、用户、业务价值。
2. 再问范围层问题，例如功能边界、优先级、MVP。
3. 最后问执行层问题，例如技术栈、时间、预算、资源。

对复杂问题尽量给出选项，降低用户回答成本。

### 第三步：迭代合并用户补充

用户每次回复后，将新信息合并进完整整理文档，而不是只显示变化部分。每轮都需要更新：

- 需求整理版本，例如“第 2 轮”。
- 已确认信息和仍待确认信息。
- 完整度评分。
- 下一轮最重要的问题。

如果用户推翻了之前的答案，应记录为需求变更，避免最终文档丢失决策过程。

### 第四步：判断是否输出最终文档

当完整度达到 85 分以上，或用户明确要求“够了”“直接输出”“生成 PRD”时，停止追问并输出最终需求规格文档。

若完整度不足但用户要求直接输出，应保留开放问题和风险假设，不伪造未确认信息。

### 第五步：生成最终需求规格文档

最终文档应包含：

- 一句话描述
- 背景与问题
- 目标与成功标准
- 用户与利益相关方
- 功能需求
- 非功能需求
- 资源与约束
- 风险与假设
- 开放问题

文档应可直接交给产品、设计、研发或项目负责人继续推进。

## 6. 领域专项追问重点

根据需求类型，优先追问不同维度：

| 领域 | 重点追问 |
| --- | --- |
| 软件 / 产品功能 | 目标用户、平台、核心流程、性能、系统对接、权限与安全 |
| AI / LLM 产品 | 模型来源、输出质量标准、延迟要求、幻觉兜底、数据隐私 |
| 数据 & 分析 | 数据来源、更新频率、指标定义、受众、报表或接口形式 |
| 业务流程自动化 | 当前流程、最痛环节、涉及角色、审批权限、外部工具集成 |
| 设计 / 创意项目 | 目标受众、参考风格、品牌限制、交付格式、使用场景 |

## 7. 推荐输出格式

技能运行过程中可以输出以下内容：

- 初步需求整理：把用户原始描述拆成结构化信息。
- 缺口问题清单：列出当前最需要确认的 2 到 4 个问题。
- 完整度评分：用 100 分制说明当前需求成熟度。
- MVP 范围建议：当范围过大或资源有限时，建议优先级和延期项。
- 需求变更记录：记录用户在多轮对话中推翻或调整的内容。
- 最终需求规格文档：输出可交付的 PRD 或需求说明。

## 8. 示例调用方式

用户可以这样提出需求：

```text
req-clarifier 帮我整理这个需求：我想做一个 AI 简历生成工具，主要面向国内用户。
```

更完整的请求：

```text
req-clarifier 我们想做一个内部审批系统，先不要写代码，帮我澄清需求、拆出 MVP 范围，并列出还需要确认的问题。
```

PRD 生成请求：

```text
req-clarifier 把下面这段想法整理成一份 PRD，并标出所有待确认项：我们想做一个客户数据看板，给销售主管看团队线索转化情况。
```

质量检查请求：

```text
req-clarifier 检查这份需求说明有没有缺口、矛盾和风险，并给出下一轮应该追问的问题。
```

## 9. 质量标准

使用该技能时，优先保证以下标准：

- 信息完整：不遗漏用户已提供的条件、限制和背景。
- 不伪造事实：未确认内容必须标注 `[待确认]` 或列为开放问题。
- 追问克制：每轮最多 4 个问题，避免把用户拖入问卷。
- 优先级明确：先澄清目标和范围，再澄清执行细节。
- 可执行：最终文档能支持后续估算、设计、开发或项目立项。
- 风险可见：显式指出关键假设、范围膨胀、资源约束和需求矛盾。

## 10. 维护建议

后续维护该技能时，建议遵循以下原则：

- 优先更新 `req-clarifier/SKILL.md` 的触发描述和核心流程，确保技能能在模糊需求场景下正确触发。
- 保持入口文件聚焦在可执行流程，不要加入过多需求管理理论。
- 如果未来新增行业专项追问清单，可以拆分到 `references/` 目录，并在 `SKILL.md` 中说明何时读取。
- 新增模板时，优先保证字段可直接复制到真实 PRD、功能说明或项目启动文档。
- 修改后检查 Markdown 和 YAML frontmatter 是否仍为 UTF-8 编码。

## 11. 快速检查清单

使用或维护完成后，可用以下清单确认质量：

- 是否说明了该技能能做什么、不能做什么。
- 是否明确了触发该技能的典型用户请求。
- 是否提供了从初步整理到最终文档的完整流程。
- 是否包含追问原则、评分规则和最终输出标准。
- 是否提供了可直接复用的调用示例。
- 是否强调未确认信息不能被当作事实。
